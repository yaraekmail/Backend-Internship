# 4. Day 1 — Sprint Planning & N+1 Diagnosis

## Objective

The first day focused on understanding and measuring database query behavior in the existing API.

EF Core SQL logging was enabled to observe the SQL commands generated by the application.

The project was also reviewed to identify possible N+1 query patterns.

## Important Finding

The existing API endpoints were reviewed first, and **no genuine pre-existing N+1 problem was found**.

To demonstrate the N+1 problem required by the training exercise, an experimental endpoint was created intentionally.

The experimental Patient-Medication access pattern produced:

```text
51 Patients
52 database commands
```

The optimized version reduced the database work to:

```text
2 database commands
```

This demonstrated how repeated related-data queries can increase database round-trips.

## Day 1 Result

The Day 1 performance target was demonstrated successfully:

```text
N+1 pattern: 52 database commands
Optimized:   2 database commands
```

The experimental endpoint was used for learning and measurement and was not documented as a pre-existing production bug.

# 6. Day 3 — Redis Caching

Day 3 introduced Redis caching for the medication catalog.

## 6.1 Redis Configuration

A managed Redis instance was used because the local Docker setup could not be used in the development environment.

Redis was registered through ASP.NET Core's `IDistributedCache` abstraction.

The application uses the cache connection string through configuration/User Secrets rather than storing the Redis credentials in source code.

## 6.2 Cache Strategy

The medication catalog uses the **cache-aside pattern**.

The flow is:

```text
Request
   ↓
Check Redis
   ↓
Cache hit ─────→ Return cached catalog
   │
   └─ Cache miss
          ↓
     Read SQL Server
          ↓
     Store in Redis
          ↓
     Return catalog
```

The catalog cache uses:

```text
Cache key:
medication-catalog:all

Expiration:
10 minutes
```

## 6.3 Cache Performance

The first catalog request produced a cache miss.

```text
Cache miss: 864 ms
```

Subsequent requests produced cache hits:

```text
83 ms
64 ms
63 ms
```

These measurements demonstrated the observed difference between the initial database-backed request and subsequent cached requests.

## 6.4 Cache Invalidation

Cache invalidation was implemented after:

* Create
* Update
* Delete

After each write operation, the catalog cache was removed.

The following GET request then loaded the updated catalog from SQL Server.

This verified that the tested write operations did not leave the catalog serving stale cached data.

## Day 3 Result

Redis caching and write-side invalidation were successfully implemented and tested for the medication catalog.

# 7. Day 4 — Database Indexing & Performance Profiling

Day 4 focused on identifying real query patterns and adding appropriate composite indexes.

## 7.1 Index Candidates

Three query patterns were identified.

### Appointments

```text
WHERE PatientId
ORDER BY AppointmentDate
```

Selected index:

```text
PatientId + AppointmentDate
```

### Medications

```text
WHERE PatientId
ORDER BY StartDate
```

Selected index:

```text
PatientId + StartDate
```

### VitalSigns

```text
WHERE PatientId
ORDER BY RecordedAt
```

Selected index:

```text
PatientId + RecordedAt
```

## 7.2 Fluent API Configuration

The indexes were added to `CardiacPatientMonitoringDbContext`:

```csharp
modelBuilder.Entity<Appointment>()
    .HasIndex(a => new { a.PatientId, a.AppointmentDate });

modelBuilder.Entity<Medication>()
    .HasIndex(m => new { m.PatientId, m.StartDate });

modelBuilder.Entity<VitalSign>()
    .HasIndex(v => new { v.PatientId, v.RecordedAt });
```

## 7.3 Migration

The EF Core migration created for the indexes was:

```text
20260915071147_AddPerformanceIndexes
```

The migration replaced the existing single-column `PatientId` indexes with the new composite indexes.

The migration was successfully applied to the:

```text
CardiacPatientMonitoringDb
```

database.

## 7.4 Before vs After Measurements

The same patient ID and the same endpoints were used before and after the index changes.

| Query        | SQL Before | SQL After | Observed Change |
| ------------ | ---------: | --------: | --------------: |
| Appointments |       5 ms |      2 ms |      3 ms lower |
| Medications  |       4 ms |      1 ms |      3 ms lower |
| VitalSigns   |       3 ms |      1 ms |      2 ms lower |

The SQL execution time decreased in all three recorded test runs.

The API elapsed time was not used as the primary indexing evidence because it also includes application-level overhead.

The measurements were collected on a small local development dataset and therefore should not be treated as production-scale benchmarks.

## 7.5 Execution Plans

Execution plans were studied as part of the training material.

However, no execution-plan result was captured during this implementation.

Therefore, no claim is made about whether SQL Server used an Index Seek, Table Scan, or another specific execution-plan operator.

# 9. Sprint 3 Retrospective

## What Went Well

* Performance decisions were based on actual query and timing measurements.
* The N+1 pattern was demonstrated using realistic seeded data.
* Eager loading and projection were compared through actual query counts.
* Redis caching included both cache-hit testing and write-side invalidation testing.
* Database indexes were selected from actual filtering and sorting patterns.
* Before-and-after SQL measurements were documented.

## What Could Be Improved

* The indexing measurements were performed on a small local development dataset.
* Execution-plan evidence was not captured.
* Query-count verification was performed manually during development.

## Sprint 4 Action

The main concrete action carried forward is:

> **Add an automated regression test for important query behavior to help prevent N+1 regressions.**

This would turn the manual query-count checks from Sprint 3 into an automated safeguard.
