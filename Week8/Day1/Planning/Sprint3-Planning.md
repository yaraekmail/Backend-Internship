# Sprint 3 Planning

## Sprint Goal

Sprint 3 focuses on improving the performance and efficiency of the Cardiac Patient Monitoring API.

The main goal is to identify inefficient database access patterns, especially the N+1 query problem, measure the actual SQL queries generated by Entity Framework Core, and use the measured results to guide performance improvements.

## Sprint 2 Retrospective Action

One improvement carried forward from Sprint 2 is to strengthen the habit of testing important authorization and ownership scenarios systematically.

For Sprint 3, this testing mindset was extended to database performance by measuring the actual queries generated by important API endpoints instead of assuming that an endpoint is efficient.

## Day 1 Performance Investigation Target

The first target was to measure the number of SQL queries generated by important list endpoints using EF Core query logging.

For the Patient-Medication access pattern investigated during Day 1, the measurable performance target was to reduce the database access pattern to a maximum of **2 database queries** for loading the Patients and their related Medications.

No N+1 problem was assumed before testing. Existing endpoints were reviewed and tested first to determine whether an N+1 pattern already existed.

## Day 1 Work Completed

### 1. EF Core SQL Logging

EF Core SQL logging was enabled in the application so that the actual SQL commands generated by the API could be observed in the terminal.

This allowed the database behavior to be measured instead of relying only on the API response.

### 2. Review of Existing Endpoints

Important existing list endpoints were reviewed and tested, including Patients, Appointments, and VitalSigns.

The tests showed that the existing endpoints did not contain an N+1 query pattern. Their database access was performed using a small number of queries rather than one related-data query per record.

### 3. Experimental N+1 Endpoint

Since the existing endpoints did not provide a genuine N+1 example, an experimental endpoint was added for learning and testing purposes:

`GET /api/Patients/nplus1`

The endpoint intentionally loads all Patients first and then loads Medications separately inside a loop for each Patient.

This was created only to demonstrate and measure the N+1 problem. It is not intended as a production endpoint.

### 4. N+1 Testing Result

The experimental endpoint was tested successfully through Swagger and returned `200 OK`.

The EF Core logs showed one query for the Patients followed by repeated Medication queries using the current Patient ID.

In the first N+1 test, there were 51 Patients.

Therefore, the expected database pattern was:

`1 + 51 = 52 database queries`

The repeated SQL commands in the EF Core logs confirmed the N+1 behavior.

### 5. Optimized Version

After confirming the N+1 problem, an optimized version was added:

`GET /api/Patients/optimized`

The optimized endpoint:

1. Loads all Patients in one query.
2. Collects their Patient IDs.
3. Loads all related Medications in one query using an `IN` condition.
4. Builds the final response in memory without sending another database query for each Patient.

### 6. Optimized Testing Result

The optimized endpoint was tested through Swagger and returned `200 OK` with the expected Patient and Medication data.

The EF Core logs showed only two database queries:

1. One query to load the Patients.
2. One query to load the Medications for all Patient IDs.

The optimized test currently contained 60 Patients, but the number of database queries remained 2.

This demonstrates that the optimized approach does not increase the number of database round trips with each Patient.

## Day 1 Outcome

Day 1 successfully identified and demonstrated the N+1 query problem.

The existing production endpoints were checked first and did not contain an N+1 pattern. An experimental endpoint was then created to demonstrate the problem, and the issue was confirmed using actual EF Core SQL logs.

An optimized version was implemented and tested, reducing the database access pattern from one query per Patient to two total queries for the tested scenario.

The measured results will be used to guide the next performance improvements in Sprint 3.

## Day 2 — Query Optimization with Eager Loading & Projection

### 1. Eager Loading with Include

The Day 1 Patient-Medication N+1 pattern was optimized using Entity Framework Core eager loading.

The endpoint:

`GET /api/Patients/eager-loading`

uses:

```csharp
.Include(patient => patient.Medications)
```

The endpoint was tested successfully through Swagger and returned `200 OK`.

EF Core SQL logging confirmed that the endpoint executed **1 database query**. The generated SQL used a `LEFT JOIN` between Patients and Medications.

### 2. Projection

A projection-based endpoint was implemented:

`GET /api/Patients/projection`

The endpoint uses `Select` to return only the Patient and Medication fields required by the API response.

The endpoint was tested successfully through Swagger and returned `200 OK`.

EF Core SQL logging confirmed that the endpoint executed **1 database query**. The generated SQL selected only the required fields rather than loading all entity columns.

### 3. Query Count Comparison

| Approach                 | Query Count | Result                                                      |
| ------------------------ | ----------: | ----------------------------------------------------------- |
| Day 1 N+1                |          52 | 1 Patients query + 51 Medication queries                    |
| Day 1 Optimized Batching |           2 | 1 Patients query + 1 Medication query                       |
| Day 2 Include            |           1 | Patients and Medications loaded using one `LEFT JOIN` query |
| Day 2 Projection         |           1 | Required fields loaded using one query                      |

The Day 2 results were verified using the actual EF Core SQL logs.

### 4. AsSplitQuery

`AsSplitQuery` was not applied during Day 2 because the current project does not contain an endpoint that eagerly loads two or more collection navigation properties.

Therefore, there was no current scenario involving multiple collection `Include` operations that required split queries to avoid cartesian explosion.

### 5. Day 2 Outcome

Day 2 successfully applied eager loading with `Include` to the Patient-Medication access pattern demonstrated during Day 1.

The query count was reduced from the 52-query N+1 pattern to **1 database query** for the eager-loading endpoint.

Projection was also implemented as an alternative approach. It also executed **1 database query** while selecting only the fields required by the API response.

The results were measured using EF Core SQL logging rather than being assumed from the LINQ code.

## Sprint 3 Backlog

Based on the Day 1 and Day 2 investigation:

- Continue reviewing important endpoints for inefficient database access patterns.
- Measure query behavior before and after performance changes.
- Avoid loading related data through database queries inside loops.
- Use eager loading with `Include` when related entity data is genuinely required.
- Use projection for list and summary endpoints when only selected fields are required.
- Apply `AsSplitQuery` when an endpoint requires multiple collection `Include` operations and split queries are appropriate.
- Continue using EF Core logging when investigating database performance.
- Review additional endpoints for possible performance improvements as Sprint 3 continues.

## Important Note

The N+1 endpoint was intentionally created as an experimental learning endpoint to demonstrate the problem after the existing endpoints were tested and no genuine N+1 issue was found.

All documented query counts and performance findings are based on actual testing and EF Core logs.
